1. Executive Summary

The Smart Expense Tracker is a full-stack personal finance application designed to combine academic DBMS rigor with a modern fintech user experience. It provides end-to-end income and expense management, periodic budget variance tracking, milestone savings goals, automated financial alerts, and an educational catalog demonstrating 20 fundamental relational DBMS queries.

The backend is architected in pure PHP 8 and MySQL without introducing external runtime dependencies (such as Node.js or Python). Security is strictly enforced using 100% prepared SQL statements, Bcrypt password hashing, session regeneration, and CSRF token protection.

3. System Workflow & Request Lifecycle

When a user interacts with the application, the request flows through a 4-tier pipeline:

The 4-Step Processing Cycle:
  1. Client Dispatch: The browser issues an HTTP request (GET or POST) to Apache on port 80.
  2. Security & Session Gate: PHP loads includes/auth.php, initializes session_start(), verifies user authentication (require_login()), and checks CSRF tokens on write operations.
  3. Database Execution: The script connects to MySQL via getDBConnection() in config/database.php and executes prepared SQL queries with bound parameter arrays.
  4. Hydration & Client Render: PHP compiles financial metrics into the HTML DOM and serializes datasets into window.DashboardData for Chart.js interactive rendering.

5. Relational Database Normalization Proofs (3NF)

The database schema (expense_tracker.sql) consists of 6 tables and 3 relational views, designed in accordance with Third Normal Form (3NF):

Normal Form DBMS Requirement Implementation Proof in This Project
First Normal Form (1NF) Attributes must be atomic; no multi-valued attributes; explicit Primary Key defined. All columns hold indivisible scalar data. Financial figures use DECIMAL(10,2) (not comma-separated strings). Each table defines an explicit surrogate primary key (e.g., user_id INT AUTO_INCREMENT PRIMARY KEY).
Second Normal Form (2NF) Must satisfy 1NF; no partial dependencies (all non-key attributes fully dependent on candidate keys). All relations use single-attribute surrogate primary keys. Non-key attributes (such as amount or description) depend entirely on the entire primary key, eliminating partial dependencies.
Third Normal Form (3NF) Must satisfy 2NF; no transitive functional dependencies (non-key attributes must not depend on other non-key attributes). In transactions, we store category_id (foreign key) but do not store category_name or icon. Category attributes are resolved via JOIN operations, eliminating update anomalies.

Relational Views

  1. v_monthly_financial_summary: Aggregates total income, expense, and net savings per user per month.
  2. v_budget_status: Dynamically computes budget utilization percentage and status (ON_TRACK, WARNING, EXCEEDED).
  3. v_category_spending: Computes category-wise counts, sums, averages, and extremes.

7. Viva Voce Defense Quick Reference

Q1: Why is DECIMAL(10,2) used instead of FLOAT or DOUBLE?
Answer: Floating-point numbers use binary approximations which produce inexact rounding errors (e.g. 0.1 + 0.2 = 0.30000000000000004). In financial systems, every cent must balance perfectly, so MySQL's fixed-point DECIMAL(10,2) data type is strictly required.
Q2: How does your application prevent SQL Injection?
Answer: We use PHP Data Objects (PDO) with native prepared statements (PDO::ATTR_EMULATE_PREPARES => false). User data is never concatenated into SQL strings; it is transmitted to the database engine separately through parameter placeholders (?), making SQL injection impossible.
Q3: How do you enforce referential integrity?
Answer: We use the InnoDB engine with foreign key constraints. When a user is deleted, ON DELETE CASCADE cleans up related transactions and budgets. For categories with recorded transactions, ON DELETE RESTRICT prevents orphaned records and preserves historical audit trails.
Q4: Why use views instead of repeated complex queries?
Answer: Views (like v_budget_status) encapsulate complex multi-table joins and calculations into virtual tables. This promotes code reusability, modularity, and allows the MySQL query optimizer to optimize execution plans.
